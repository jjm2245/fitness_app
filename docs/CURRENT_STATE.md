## 1. Stack & versions

- **Next.js 16** (App Router; middleware is `src/proxy.ts` — the "proxy" rename;
  Edge runtime uses Web Crypto not `node:crypto`; dynamic-route `params` are a
  `Promise` and must be awaited). **React 19.** **TypeScript 5.**
- **Postgres** via **Drizzle ORM** + `pg` driver. Schema in `src/db/schema.ts`,
  migrations in `drizzle/` (drizzle-kit), applied with `npm run db:migrate`.
- **IndexedDB** via `idb` — the offline store, **version 4**, in
  `src/lib/sessionStore.ts`. This is the load-bearing offline layer.
- **Vitest** (unit) with `fake-indexeddb`. No E2E/browser test runner — UI is
  verified by driving the local dev server + manual phone testing.
- **PWA:** `public/sw.js` (hand-written service worker) + `manifest.webmanifest`.
- **Prod:** Vercel (auto-deploys `main`) + Neon Postgres. Live at
  **https://fitness-app-self-pi.vercel.app** (health: `/api/health`).

## 2. Run it locally

Requires Node ≥20 and a local Postgres. Env in `.env` (never committed):
`DATABASE_URL`, `APP_PASSCODE`, `SESSION_SECRET`.

```bash
npm install
npm run db:migrate        # apply migrations to DATABASE_URL
npm run db:seed           # curated exercise graph (idempotent)
npm run db:seed:library   # free-exercise-db ingest (slow; idempotent)
npm run dev               # http://localhost:3000  (or: preview_start "fitness-app")
npm test                  # vitest
npm run build             # next build (must be clean)
npm run db:check          # fail if DB schema is behind the code's migrations
npm run docs:refresh      # regenerate the AUTOGEN block in this file
npm run docs:check        # fail if the AUTOGEN block is stale
```

`release` = `db:migrate && db:seed && db:seed:library`. Neon's **pooled**
endpoint chokes drizzle-kit migrations — use the **direct** endpoint (strip
`-pooler` from the host) for `db:migrate` against prod. **Shipping a schema change
to prod: follow [`RUNBOOK.md`](RUNBOOK.md)** (migrate-before-deploy order, the
endpoint split, before/after counts, the health/db:check gates).

  `movementPattern` (nullable — null ⇒ `untagged`, not substitutable),
  `canonicalName`/`libraryId` (library pairing), `affectedStructures[]` (e.g.
  `lumbar_spine`), `unilateral`, `description`, `loadType`, `portable`. Muscles in

  + `builtInWeight` + `pulleyRatio`/`counterweightLb`/etc + free-text `notes`.
  `exercise_equipment` join. Never rename the id (history-safe); rename = edit
  `label`; merge duplicates = re-point references then delete (like exercise
  collapse).
- **`workout_logs`** — a session. `clientSessionId` (client-owned identity,
  unique), `date` (stable calendar day — the display/sort anchor), `finishedAt`
  (re-stamps on every finish — **not** a display anchor), **`firstFinishedAt`**
  (stamped once; the display/sort time anchor) + **`firstFinishedSource`**
  (`'user'` when set via the date/time editor).
- **`session_exercises`** — the ordered performed **occurrences** (session-model
  v2). `clientInstanceId` (client-owned), `orderIndex`, `source`, **`completed`**
  (the "done" check — synced so it survives a PWA wipe). The same exercise can
  occur multiple times (repeats).
- **`set_logs`** — one row per set. `sessionExerciseId` (occurrence link,
  `set null` on occurrence delete), `load` (the **effective total** = entered +
  built-in offset), `loadEntered` + `builtinOffset` (the components), `reps`,
  `effort` (the primary effort tag; `rir` optional exact), `setIndex`,
  `setType`, `equipmentId` + `equipmentType`, **`loggedAt`** (client-stamped —
  drives rest derivation), **`restSeconds`** + **`restSource`** (`timed|derived|
  user`; null = honest-unknown, never fabricated — stored as *restBefore*, so N
  sets ⇒ N−1 rests), **`dropSetGroup`** (drop-set link), **`side`** (`left|right|
  both` for unilateral).
- **`cardio_logs`** — separate shape (duration/incline/speed/…); structurally
  invisible to the core (core reads only `set_logs`).
- Later-phase tables exist but are unused: `body_metrics`, `recovery_metrics`,
  `nutrition_entries`, `progress_photos`, `form_checks`, `injury_flags`, `profile`.

Local (IndexedDB v4) stores: `sessions`, `occurrences` (keyed `instanceId`),
`sets`, `cardio`, `completed` (**legacy — completion now lives on the occurrence;

## 5. API surface

See the AUTOGEN routes table. Shape notes: occurrences sync via
`POST /api/session-exercises` (whole ordered list; prunes removed rows but
**refuses to delete an occurrence that still has logged sets** — the wrong-side-

create+PATCH carry all logging-depth fields.

## 6. Offline / sync architecture (`src/lib/sessionStore.ts`) — most bug-prone

The UI **always reads the local store**, never a network round-trip; `sync()`
reconciles in the background. `sync()` is **serialized** via `syncChain` (two
rapid calls must not double-POST — that duplicated logged sets historically).

**Drain order (matters):** occurrences → sets → cardio → **second occurrence
pass** → finish → date/time (meta) → queued deletes. Occurrences go first so
set-logs can link by `clientInstanceId`. The second occurrence pass exists
because a set-bearing occurrence the client removed is *kept* on pass 1 (guard),
its sets delete in the set loop, then pass 2 prunes the now-empty row — heals a
legit remove-with-sets in one sync.

**Dirty flags & pending signals** (all surfaced in the sessions-list "not synced
· <reason>" badge):
- `occurrencesDirty` (session-level) — the ordered list has an un-pushed change
  (add/remove/reorder). Dirtiness is a property of the *list*, so it survives
  removing the last occurrence. Cleared when the list POSTs cleanly.
- `occurrenceConflict` — the server kept occurrence(s) this device tried to drop
  because they carry logged sets the device doesn't have ⇒ **this device is
  behind**. Heal = **Pull from server** (`rehydrateLocalFromServer`), not
  Reconcile.
- finish arm: `finishedAt && !finishSynced` (reconciled from the server on the
  sessions page — a server-confirmed finish never shows false "not synced").
- `metaDirty` — un-pushed date/time edit.
- per-set `syncState` (`pending_create|synced|pending_update|pending_delete`).

**Directional heals (explicit, never automatic):** `reconcileOccurrenceList`
(local → server; re-POST local list, history-safe via the prune guard) and
`rehydrateLocalFromServer` (server → local; wipe local session, rebuild from the
server copy). We **detect and warn, never auto-resolve** — local isn't reliably
the source of truth (after a wipe it hydrates from the server).

**`healSingletonDropGroups`** runs on log-page load: nulls any orphaned singleton
drop group (legacy stray "+ Drop" tags), syncing the clear idempotently.

**IndexedDB migrations** live in `migrateSessionDb(db, oldVersion)` and are
**additive by default** — the destructive `oldVersion < 4` drop is a documented
historical one-off; new versions are `if (oldVersion < N)` create-only blocks.
Guard test: a future bump preserves data (proven in isolation).

## 7. Local vs production

Vercel auto-deploys `main`, but **migrations are manual** — shipped code can
outrun the prod schema. `/api/health` returns 503 when `applied <
EXPECTED_MIGRATIONS`; `db:check` fails on drift. **Migrate-then-deploy**: apply
the migration to prod (direct Neon endpoint) *before/at* the deploy that needs
it, else the affected API 500s. Additive columns are safe; propose before any
prod write. There is no automated prod-migration step yet — a manual runbook is
the current mechanism (see DECISIONS).

three-tier emphasis drift** recorded in SPEC-DRIFT §7. That entry stays untested
until v2 actually sums `exercise_muscles.emphasis` on screen.

It expects `SetLogInput[]` (the shape `loadSetLogInputsForExercise` produces,
carrying `exerciseId`, `date`, `setType`, `load`, `reps`, `rir`, `machineId`) plus
`exercisesById: Record<string, { muscles }>`. It returns **counted sets per
muscle**, not tonnage — a set contributes its stored emphasis, and warm-ups
contribute nothing.

**Read this before trusting the spec's wording.** Spec §7 states the rule as
"1.0 for the primary muscle and 0.5 for meaningful secondaries; warm-ups 0" —
two tiers. The implementation uses the seed's **three**-tier stored emphasis, and
production matches it:

| emphasis | rows in `exercise_muscles` |
|---|---|
| 1.0 (primary) | 869 |
| 0.5 (meaningful secondary) | 1681 |
| **0.3 (minor secondary)** | **35** |

So a minor secondary contributes 0.3, which the spec's flatter rule does not
describe. This was a deliberate choice (see DECISIONS) and it means **any total
computed from the spec's wording will disagree with `volume.ts` by design.** Use
the code, not the sentence.

### The muscle graph

`muscles` (24 rows) and `exercise_muscles` (2,585 links) are the graph behind
per-muscle volume. Fully populated across the library, not just the exercises in
use — **28 distinct exercises appear in `set_logs` against 878 in the library**,
so any "volume by muscle" surface reads a graph far larger than the training
history that references it. That is intentional (the library ships whole so
`set_logs.exercise_id` always resolves), but it means the graph size is not a
proxy for how much has actually been trained.

### The lane shape of the real data (read 2026-07-30 — re-check before building)

The structural question for a per-exercise view is how many lanes exist in
practice, and the answer is nearly unanimous: **26 of 28 logged exercises have
exactly one lane; 2 have two; none has three or more.** Median **2.5 sessions**
per exercise (range 1–6). The two multi-lane cases are both genuine, not data
gaps: Machine Shoulder (Military) Press (VSL18 + LifeFitnessShoulder) and Seated
Back Extension Machine (VSL02 + a dumbbell portable lane). Every NULL
`equipment_id` row carries a portable snapshot type (bodyweight / dumbbell) —
**zero unattributed context-bound rows** remain.

Design consequence, stated but not designed here: a permanent lane switcher is
dead chrome on 26 of 28 screens, and stacked per-lane sections have no case that
overflows a phone today — whatever v1 builds should treat multi-lane as the
exception it is, while still honouring it where it's real.

### Lane semantics — the constraint on every per-exercise chart

A **lane** is `(exercise, unit)`, and loads are **not comparable across lanes**.
190 lb on VSL13 is a best on VSL13, not on "Butterfly" generally: different cams,
pulleys and starting resistances produce different numbers for the same effort.
Everything lane-aware in the app already honours this — PRs, the `best` line,
progression re-baselining on a machine change, the recalibration note.

**A per-exercise chart that plots load over time without splitting by lane will
draw a cliff every time a machine changed and call it a regression.** The lane
key is `laneKey()` in `src/lib/equipment.ts` (unit id → else `"type:unspecified"`
→ else portable/null); use it rather than re-deriving the rule.

### Everything Stats would show is COMPUTED, never stored

PRs, progression verdicts, the `last …` line, `firstWorkingSet`, session
duration, volume, the plate-increment suggestion — all derived from `set_logs` on
each read. There is no cache to invalidate and no stored copy that could
disagree; equally, there is no precomputed table to read from, so Stats computes
like everything else does. Ordering rules matter when doing so: the shared
adapter carries **no `ORDER BY`** (its row order was measured as
load-descending), and a drop segment shares its parent's `set_index` — order by
`(set_index, id)` and treat the lowest id in a `drop_set_group` as the parent.

### Context tables that exist and are populated

- **`body_metrics`** — dated weigh-ins, one row per date, canonical lb. A time
  series, not a current value; back-dated rows are valid and expected.
- **`timeline_notes`** — dated free-text spanning the gaps *between* sessions
  (illness, travel, deload). `end_date` NULL means still ongoing. **Inert by
  construction**: nothing in the engine reads it, unlike `injury_flags`. Absence
  of a note over a gap means nothing was recorded, never that nothing happened.

## 11. Data-shape constraints (read before designing anything numeric)

Three facts about the data every numeric surface — Stats, and later any
LLM-facing summary — inherits. Three fresh advisors derived the second and third
independently from the other docs; stating them here is cheaper than having
every reader re-derive them.

### Effort coverage is low and stays low

Effort is recorded on **71 of 244 sets — 29%** in production today, and **this is
expected to stay low.** The owner logs to a rep target, not to failure, so most
sets legitimately have nothing to record.

It is not a data-quality problem to be fixed. It was investigated for the
progression work and the conclusion was that **effort cannot be inferred**:
within-session rep decay was considered as a proxy and rejected, because 10/10/10
is the expected shape of an easy session and a hard one alike. See DECISIONS
2026-07-28.

**Consequences for anything built next:**

- The core currently treats an untagged set as *at target*
  (`s.rir ?? context.targetRir`), which biases `true_stall` and `increase_load`
  toward firing on ~71% of the data. That assumption is recorded as a deferred
  finding, not endorsed.
- **Any Stats or LLM surface leaning on effort must degrade honestly** — say
  "effort not recorded" rather than assume, average, or impute. An effort-weighted
  chart computed over 29% coverage and drawn as though it were complete is a
  confident lie.
- Load, reps, sets and time remain the primary signals, and that is fine: those
  are what actually drive hypertrophy.

*(The figure moves as more is logged — it was 24% (52/215) when the progression
brief measured it in July. The constraint is the shape, not the number.)*

### Bodyweight lanes log `load 0` BY DESIGN — branch, don't degrade

Pullups, Dips and Captain's Chair: **25 working sets, load min 0, max 0**, and
that is correct — load measures what was *added* to the body (the closed
bodyweight decision). Consequences, stated so they are met here rather than
discovered on screen:

- **A load-based chart draws a flat line at zero.** Forever.
- **PR detection is structurally impossible** on these lanes — a PR requires
  strictly greater, and every load ties at 0. Correct, not a bug (DECISIONS
  2026-07-29).
- **Volume-load is 0 every session**, which is also why `regression` can never
  fire there — the highest-ranked open SPEC-DRIFT entry ("Regression detection
  is structurally unreachable on bodyweight lanes").

Any load-based view needs a **separate branch** for these lanes (reps are the
signal there), not a degraded rendering of the same one.

### Progression often happens in reps, not load — measured, not anecdotal

`MIN_HISTORY = 1` exists in DECISIONS precisely because the `last` reference is
typically one working weight with several rep counts (`120 lb × 12, 11, 10`) —
requiring two distinct loads "silenced the check on essentially every real
exercise."

Measured against prod (2026-07-30), session→session transitions of the **top
working load per lane** (warm-ups and drop segments excluded):

| transitions | load up | load down | **load flat** | flat *with* rep progress |
|---|---|---|---|---|
| 50 | 14 | 14 | **22 (44%)** | 7 |

So on **44% of transitions a load line does not move**, and about a third of
those flats carry real rep progress — `110 × 11 → 110 × 12, 12` is a measurably
stronger session that a load-only chart renders as nothing. Lane-level: of 25
lanes with 2+ sessions, 21 have moved load at least once; the 4 that never have
are the three bodyweight lanes plus Dumbbell Shrug. **Load and reps have to
travel together in the same mark** — a load-only view is flattest exactly where
progress is most often real.

**Now consumed by shipped code:** Stats v1's delta grammar renders state 2
(`same load · N more reps`) in the BRIGHT tier — rep progress at a held load
reads as progress, not as nothing. Future numeric surfaces have a precedent to
match rather than a constraint to rediscover.

## 12. Core generality self-check

`src/core/*` carries **no** routine-specific or equipment-specific literals
(exercise ids, machine names, offsets, equipment types). Equipment is handed to
the core only as an opaque **lane key** string (`laneKey` in `src/lib/equipment.ts`,
outside core). Run `grep -rn` for equipment types / offsets / exercise ids in
`src/core` every session — it must stay empty (test fixtures excepted).

## 13. Traps (things that waste time or cause damage)

- **IndexedDB migrations must stay additive** — `migrateSessionDb` creates only;
  never `deleteObjectStore` a store carrying data forward (silently eats unsynced
  in-flight work). The `oldVersion < 4` drop is a historical one-off, not a
  template. Keep the data-loss guard test green.
- **`sync()` must stay serialized** (`syncChain`) or duplicate logged sets return.
- **Occurrences sync before sets** — set-logs link by `clientInstanceId`, which
  must exist server-side first.
- **The prune guard is load-bearing** — `/api/session-exercises` must never delete
  an occurrence that still has logged sets/cardio (a stale/wiped client re-POST
  would otherwise destroy history). The paired client two-pass heals legit removes.
- **`finished_at` is not a display anchor** — it re-stamps on every finish. Show/
  sort by `date` + `firstFinishedAt`. All user-facing times render **local**
  (client components + `toLocale*`); date-boundary logic uses local calendar parts
  (UTC `toISOString().slice(0,10)` files evening sessions to the next day).
- **Never mass-delete or migrate prod without sign-off.** Migrate-then-deploy.
- **Keep exercise & equipment ids stable** — logged history references them.
- **drizzle-kit `generate` needs current snapshots** — hand-writing a migration
  without regenerating the snapshot makes the next `generate` hit an interactive
  rename prompt (non-TTY = crash). If you hand-write SQL, keep the snapshot honest.
- **`_resetDbForTests()` is test-only** (deletes the whole IDB).
- **Secrets:** env-var names only in docs; the Neon credential is exposed +
  unrotated (owner's deferred task) — never commit connection strings.
